# v1.2 plan: proposals, safety net, and housekeeping

Status: planned. Tracked in the **v1.2.0** milestone on GitHub.

Headline feature: **RSVPs and proposals**. Alongside it: login rate limiting, trash/undo, an MIT
license, and the docs and test groundwork that make those safe to build.

## Decisions already made

| Question | Decision |
|---|---|
| License | **MIT.** The project is meant to be used by anyone, and MIT is the simplest permissive license. |
| Trust model | The shared group password stays **trust-based**. Anyone with the password can edit anyone's events and respond on anyone's behalf. No sensitive data is stored, and this lets someone add something for a friend on request. |
| Delete confirmations | Deleting a **single** event no longer asks "are you sure?": an **Undo** toast replaces it. Deleting a **series** keeps a confirmation (revisit after real use). |
| Proposal rules | See "Proposals" below. In particular: a response is the source of truth, and only **yes** responses become events. |

## Findings that shaped the plan

- **User text is never escaped.** Titles, names and notes are interpolated into `innerHTML`
  (`app.js`, `assistant.js`, `modal.js`) with no escaping helper. A `<` in a title breaks the
  layout; a crafted title runs script in other members' browsers. Proposals add more typed text, so
  this is fixed first.
- **Events are per-person blocks** (one `owner` each) and the scheduling assistant treats every
  event as busy time. A proposal must therefore *not* be an event until it is confirmed.
- **The server does no timezone math** today; all conversion is in `static/lib.js`. Confirming a
  proposal needs it server-side. This is the largest technical risk.
- **Deletes are permanent** behind a `confirm()`, and `main.py` is near the 600-line file limit.

## Phase 0: groundwork

1. **LICENSE (MIT).**
2. **Tests and CI.** Pytest for API, auth, series scopes, backup and ports; `node --test` for
   `lib.js`; GitHub Actions on every push and PR.
3. **Escape user text** with one `esc()` helper applied everywhere, with tests.
4. **Pin dependencies**, add Dependabot, and bump the Node-20 GitHub Actions.
5. **Split `main.py`** into `auth`, `db`, `events` (and later `trash`, `proposals`). A pure
   refactor commit; tests prove behavior is unchanged.
6. **Migration framework.** Replace ad-hoc `ALTER` statements with an ordered list keyed on
   `PRAGMA user_version`. Each migration runs in a transaction, and the app snapshots the database
   first (`calendar.db.bak-pre-vN`). A golden v1.1 fixture database is migrated in tests.

## Phase 1: login rate limiting

- Per-client-IP backoff (for example 5 failures, then 1 minute, escalating to 15), `429` with
  `Retry-After`, a countdown on the login page, failures logged, success resets the counter.
- **Behind a tunnel every request arrives from localhost**, so a naive limiter would let one
  attacker lock everyone out. Read `CF-Connecting-IP` only when the direct peer is loopback.
- No hard global lockout (that would be a denial-of-service lever); a soft global slow-down only.
- Set the session cookie's `Secure` flag when served over HTTPS.
- Tests: lockout, expiry, per-IP isolation, header-trust rules.

## Phase 2: trash and undo

- Soft delete: `deleted_at` and `deleted_batch` on events, so deleting 100 shifts is one undoable
  unit.
- **Main risk:** every query must ignore trashed rows (lists, series info, scoped edits and
  deletes). Centralize the filter in one helper and test that trashed events never appear anywhere.
- API: list trash (grouped by batch), restore, purge, and auto-purge after 30 days
  (configurable).
- UI: an Undo toast for about 10 seconds after any delete, plus a Trash panel (Restore, Delete
  forever, Empty).
- Proposals use the same mechanism.

## Phase 3: RSVPs and proposals

**Core idea:** a proposal is a tentative slot that blocks nobody's time. When someone confirms it,
the server creates a normal event for each person who said yes. The per-person timeline, the
scheduling assistant and backups keep working unchanged.

Data (two migrations):
- `proposals`: proposer, tag, title, detail, note, day, start/end in the proposer's timezone,
  status (`open`, `confirmed`, `cancelled`), trash fields.
- `proposal_responses`: one row per (proposal, user) with `yes`, `maybe` or `no`.
- `events.proposal_id`: nullable link from a derived event back to its proposal.

Rules:
- Anyone can create, respond for anyone, and confirm (trust model).
- Changing a proposal's day or time resets other people's responses to "waiting" and shows a
  "time changed" note.
- Confirmed proposals still accept responses: **yes** creates that person's event; **maybe** or
  **no** removes it. The response is the source of truth and the event is derived.
- Deleting a derived event counts as "can't make it".
- Only **yes** responses become events; maybes do not.
- Proposals never count as busy time in the scheduling assistant.

**Timezone risk.** A confirmed event is copied into each attendee's own local time, so the server
needs real conversion (`zoneinfo` plus the `tzdata` package, also bundled in the Windows build).
Two hard cases: day rollover (11pm Pacific is 2am Eastern the next day) and events that cross
midnight in the attendee's zone, which the current one-local-day model cannot store. Plan: split
derived copies at midnight into two rows. Prototype this first, with tests across DST boundaries.

UI:
- A "make this a proposal" toggle in the existing add dialog (reuses the form).
- Dashed proposal chips on the calendar and snapshot, with a tally (yes / maybe / waiting),
  Yes/Maybe/No buttons, a "responding as" selector, and Confirm.
- An "open proposals" strip for ones waiting on you, so they are not hidden unless you click that
  day.
- A conflict warning when someone says yes while they already have a clashing event.
- New `proposals.js` and `trash.js` to stay under the file-size limit.

## Phase 4: docs and release hygiene

- `SECURITY.md` (enable GitHub private vulnerability reporting), `CONTRIBUTING.md`,
  `CHANGELOG.md`, issue templates.
- README: proposals, trash, rate limiting, a security-model note (trust-based by design),
  screenshots.
- `THIRD_PARTY_NOTICES.txt` generated at build time and shipped in the installer (check the
  `pystray` license terms; to our knowledge LGPL-3.0).
- Hosting guide: the client-IP header used for rate limiting.

## Release

1. Teach the release workflow to publish `-rc` tags as prereleases (today the tag must equal
   `version.py` exactly).
2. `v1.2.0-rc1`, then an upgrade test: install v1.1.0 over a copy of real data, upgrade, confirm
   nothing is lost.
3. `v1.2.0`.

Downgrades are not supported (migrations are one-way). The installer and docs say to restore the
pre-upgrade backup instead.

## Out of scope for v1.2

Multi-option polls ("Friday 8pm or Saturday 7pm"; designed so it can arrive later as an additive
migration, with no speculative tables now), notifications and webhooks, an iCal feed, more
timezones, and any change to how authentication works.

## Delivery order

LICENSE, then Phase 0 (starting with the test and CI scaffold), then rate limiting, then trash
(backend, then UI), then proposals (timezone prototype, backend, UI, polish), then docs, then the
release candidate. Each step is a separate, green PR.
